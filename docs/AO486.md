# ao486 (FPGA 486)

The one target DOSy++ has never run on, and the only one that is real
hardware. This is what to do when a board is available, and what the
answer has to be.

Nothing here has been executed: there is no ao486 core and no DE10-Nano in
the development environment. Everything below is either derived from the
core's own documentation or is a gate defined so that passing it means
something. It is written down rather than attempted so that the next person
with the hardware spends their time running tests instead of inventing
them.

## What you need

| Piece | Which one |
|---|---|
| Core | an ao486 build **with the NE2000 ISA card**. Mainline has historically had no NIC -- networking was serial/PPP. A community fork adds a real NE2000 (16KB packet RAM, station PROM, 16-bit remote DMA, MAC derived per board). Pin the build you test and write the version into the README. |
| Packet driver | Crynwr `NE2000.COM`, the same ISA driver the DOSBox-X rigs use -- not `PCIPKT.COM`, which is for the browser host's PCI card. `make pktdrv`. |
| DOS | anything that runs a DJGPP binary. The rigs use FreeDOS 1.3. |
| Files | `DOSYPP.EXE`, `CWSDPMI.EXE`, `NE2000.COM`, a `WATTCP.CFG`. `make dosfiles` collects them. |

## WATTCP.CFG

Static, not DHCP, unless the core's network setup provides a server:

```
my_ip      = 192.168.1.50
netmask    = 255.255.255.0
gateway    = 192.168.1.1
nameserver = 192.168.1.1
```

The DOSBox-X image uses `dhcp` because slirp hands out leases, and the v86
image is static because Watt-32 will not take v86's JavaScript offer. Which
of those ao486 resembles depends on how its NIC is bridged; try DHCP first
and fall back.

## The gates

In order, because each one needs the last to have worked.

1. **It runs.** `DOSYPP.EXE --batch -p 1511 <hub>` prints a session id.
   This exercises DJGPP, CWSDPMI, protected mode, the packet driver and
   Watt-32. The core runs Windows 95 and Quake, so a failure here is a
   driver or an address problem, not a CPU one.
2. **The display is right.** `--vgacheck` draws the UI and reads 0xB8000
   back, reporting how many of the 2,000 cells differ. It should be zero.
   `--rows 50` then repeats it for 4,000 cells with the 8x8 font, which
   depends on the core's BIOS honouring int 10h AX=1112.
3. **The keyboard is right.** `--kbdtest` injects scancodes through the
   controller (0x64 <- 0xD2) and checks the UI reacted. This is the int 9h
   handler on real hardware, which is the thing most likely to differ from
   an emulator.
4. **Hashing throughput.** `HASHBENC.EXE` from `make dos-bench`. The
   DOSBox-X profile at 25,000 cycles gives 521 KB/s; a DX2-66-class core
   should be in that region. A number far below it means the core's memory
   path is the limit, which matters for the share workflow (33 minutes a
   gigabyte at 521 KB/s).
5. **The sustained-transfer gate: a 100MB download must complete.**
   This is the one that exists because of ao486 specifically. Large
   transfers have been reported to stall in bursts, attributed to the
   core's PIO implementation rather than to the NIC. A chat client would
   not notice; a file transfer client is nothing but this.

   Run it with the same rig the other targets use:

   ```sh
   XFER_SIZE=100000000 XFER_RUN_SECS=1800 XFER_ALARM=2400 \
       ./test/dos/run-dosbox-xfer.sh
   ```

   On ao486 the DOS side is the real machine rather than DOSBox-X, so the
   rig's guest half has to be run by hand with the same arguments; the host
   half (stub hub, uploader, hash check) is unchanged.

   What to look for, in this order:

   - **It completes at all.** The rig verifies the TTH, so a stall that
     resumes is a pass and a stall that does not is a timeout.
   - **The throughput line.** The rig prints `moved N bytes in Ts -- K
     KB/s`. Compare it against the same command on DOSBox-X: 20MB moves at
     about 80 KB/s there including boot, login and hashing. A sustained
     transfer that is an order of magnitude slower on the FPGA is the
     reported PIO weakness, not a client bug.
   - **Whether it resumes.** Kill the transfer part way and run it again.
     Segmented downloads verify each part against its own node of the
     Merkle tree, so a resumed transfer re-checks what is on disk and
     fetches only what is missing. A core that stalls is exactly the case
     this was built for.

6. **The music.** `--music-report` prints what the Sound Blaster has
   played and what the mixer has fed it, once a second. On real hardware
   with a real card this is the first time either number means anything --
   DOSBox-X proves the ring advances, not that a speaker makes a noise.

## What is already known to be fine

- **No FPU.** Some 486 cores are SX-class or have incomplete x87. The whole
  program is built `-msoft-float`, so a stray `double` fails at link time
  rather than trapping on the board. Tiger and TTH are 64-bit integer work
  by construction.
- **Memory.** The client runs in 16MB with the share index, the bzip2
  decompressor and a 16KB sound ring. `make dos-bench-run` reports the
  index at 56 bytes per file.
- **The driver API.** Watt-32 talks to the packet-driver interrupt and
  nothing else, which is why one binary covers real hardware, DOSBox-X and
  a browser tab. See [`PKTDRV.md`](PKTDRV.md).

## If the NE2000 fork is not available

The client needs a packet driver and nothing else, so anything that
presents one will do: a serial SLIP/PPP driver would work at serial speeds,
and the browser host's relay architecture (plaintext on the LAN, TLS
upstream) is unaffected by which NIC is underneath. It would not be a
meaningful transfer test, but it would answer gates 1 through 4.

# Browser host (v86)

DOSy++ in a browser tab, connected to a real ADC hub. **The DOS binary is
unmodified** — the same `DOSYPP.EXE` that runs on a 486.

```sh
./tools/fetchv86.sh                   # v86 engine + BIOS -> web/vendor/
./tools/mkv86img.sh                   # disk images -> web/images/
./tools/wisprelay.py                  # relay + web server on :8086
open http://127.0.0.1:8086/
```

Then inside DOS: `DOSYPP 10.77.0.1`

## How it fits together

```
  browser tab
 ┌─────────────────────────────────────────┐
 │  v86                                    │
 │  ┌───────────────────────────────────┐  │
 │  │ DOS guest                         │  │
 │  │   PCIPKT.COM (packet driver)      │  │
 │  │   Watt-32                         │  │       wisprelay.py
 │  │   DOSYPP.EXE                      │  │     ┌──────────────┐
 │  └──────────────┬────────────────────┘  │     │ Wisp server  │
 │      ethernet   │ frames                │     │      +       │
 │  ┌──────────────▼────────────────────┐  │ WS  │ static files │     ADC
 │  │ WispNetworkAdapter               ─┼──┼────▶│      +       │────▶ hub
 │  │  ARP, DHCP, TCP state machine     │  │     │ optional TLS │
 │  └───────────────────────────────────┘  │     └──────────────┘
 └─────────────────────────────────────────┘
```

v86 emulates an **RTL8029** (PCI NE2000). Its Wisp adapter answers ARP and
DHCP in JavaScript and converts each guest TCP connection into a Wisp stream
over one WebSocket. `tools/wisprelay.py` terminates those as real TCP.

## Addressing — the part that surprises people

v86 sends **the dotted-quad the guest dialled** as the Wisp `CONNECT`
hostname. There is no DNS in the path by default, and the relay never sees a
hostname. So destinations are configured as *mappings*: the guest dials a
sentinel address, the relay substitutes the real hub.

```sh
# default: 10.77.0.1 -> the local stub hub
./tools/wisprelay.py

# a real plaintext hub
./tools/wisprelay.py --map 10.77.0.1=hub.example.org:1511

# an ADCS hub -- TLS terminates at the relay, no crypto in DOS
./tools/wisprelay.py --map 10.77.0.1=adcs.example.org:2780:tls
```

Guest gets `192.168.86.100`; gateway and DNS are `192.168.86.1` (v86
defaults, stated explicitly in `web/index.html`).

The v86 image configures that **statically**, in its own `WATTCP.CFG`. v86's
adapter does answer DHCP in JavaScript, but Watt-32 will not take the offer —
with the driver loaded and working you get `Configuring through DHCP..failed`,
then BOOTP and RARP fail too. v86's addresses never change, so static is both
deterministic and quicker to boot. The DOSBox-X image keeps `my_ip = dhcp`,
which is right for slirp; neither should be changed to match the other.

`--allow-direct` lifts the mapping requirement and lets the guest reach
anything. It is **an open TCP proxy** — development only, never exposed off
localhost.

## Disk images

`tools/mkv86img.sh` builds two, into `web/images/`:

| Image | What |
|---|---|
| `boot.img` | 1.44MB bootable FreeDOS 1.3 floppy (from the Floppy Edition archive, `144m/x86BOOT.img`), with `FDAUTO.BAT` replaced so it calls `C:\GO.BAT` instead of the installer |
| `dosypp.img` | 32MB FAT16 "hard disk" holding `DOSYPP.EXE`, `CWSDPMI.EXE`, `PCIPKT.COM`, a static `WATTCP.CFG`, `GO.BAT` and `AUTOTEST.BAT` |

Two images because making a FAT16 hard disk bootable requires DOS's own `SYS`
command, which would mean running DOS to build the image. Booting an
unmodified FreeDOS floppy with everything on a roomy `C:` avoids that, and the
data image can be rebuilt without touching the boot media.

Needs `mtools` (`brew install mtools`).

## Files you must supply

`mkv86img.sh` reads these from `dosbox-x/c/` and warns rather than failing if
they are absent:

| File | Where from |
|---|---|
| `DOSYPP.EXE` | `make dos` (or `tools/dosmake.sh`) |
| `CWSDPMI.EXE` | ships with DJGPP |
| **`PCIPKT.COM`** | Realtek RTL8029 PCI packet driver (`make pktdrv`) |

The packet driver is the one genuine difference from every other target:
**v86's NIC is a PCI RTL8029, so `NE2000.COM` will not find it** — the ISA
driver probes fixed I/O ports. You need Realtek's `PCIPKT.COM`, which walks
the PCI bus itself and so needs only a software interrupt. Watt-32 is
unaffected: the packet-driver API is identical, which is the whole reason one
binary covers real hardware, DOSBox-X and the browser. See
[`docs/PKTDRV.md`](PKTDRV.md).

## Why the relay serves the web pages too

Convenience, and one fewer thing to get wrong: the relay serves `web/` on
the same port it accepts WebSockets on, so there is one origin, one process
and no mixed content.

It also sends `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp`. Those were once load-bearing
-- a v86 built with threads needs `SharedArrayBuffer`, which needs them --
but the pinned engine's WebAssembly memory is **unshared** and
`libv86.mjs` never mentions `SharedArrayBuffer`, so this build does not
need cross-origin isolation at all. That is what makes publishing to a
static host possible (`docs/PAGES.md`), and `make test-pages` checks it
rather than trusting it: a future engine could change it freely, since the
engine is fetched and not vendored.

## Persistence

A browser tab forgets everything on reload, which for this client means a
new CID, a re-hashed share and the favourites gone. The page therefore
keeps the **whole machine state** in IndexedDB: **Save session** writes it,
closing the tab writes it, and the next boot restores it. **Forget** throws
it away.

The state is tens of megabytes (39MB for a 16MB machine), which is why it
is IndexedDB rather than localStorage, and why it is saved on demand rather
than on a timer. A state from a different v86 build will not restore; the
page says so and boots fresh rather than showing a blank screen.

`make test-v86-state` tests the half that can go wrong without a browser:
v86's own save/restore with DOS running inside it. It boots until DOSy++ is
up, notes the identity, saves, destroys the emulator, builds a fresh one,
restores, and checks the machine *carries on* with the same CID -- a
restore that produced a machine which merely did not crash would prove
nothing. The IndexedDB layer itself is browser-only and is not tested here.

## Testing without a browser

```sh
make test-relay     # the relay alone, against the stub hub
make test-v86       # the whole stack: v86 + DOS + driver + Watt-32 + relay
```

`make test-v86` is the real check. It boots `web/images/` in v86 from Node,
with DOS output captured over COM1 rather than scraped off the text screen,
and passes only when DOSy++ itself reports a session id:

```
Packet driver for RTL8029, PCI version 1.1
My Ethernet address is 00:22:15:6B:93:8B
  ISID  [info]  AAAB
PHASE 0 OK
```

`make test-v86-xfer` is the transfer gate: a file leaves the tab. The guest
shares two demo files from its own image, a host client searches the hub,
queues one and downloads it, and the bytes are checked against the
original's hash.

The direction is forced by what Wisp can do. It carries outbound streams
only -- nothing can dial into a browser tab -- so a transfer only works
when the guest is the side doing the dialling, which in ADC means the guest
is the **uploader** answering an active downloader's CTM. The host client's
address is advertised by the hub as a second sentinel (`10.77.0.2`) that
the relay maps to its real port, so the guest needs no DNS and no knowledge
of the host, exactly as with the hub mapping.

`make test-v86-dl` is the one that matches what the demo claims: the guest
searches the hub for a real game, downloads it from a peer it had to dial
through a WebSocket, verifies it against the hash the hub advertised, and
unpacks the executable -- all read back off COM1 from DOS's own `DIR`
output.

The file really is served, by `tools/stubhub.py --serve`: one node on the
stub hub whose share is a directory of free DOS packages, speaking the
uploading half of the client-to-client protocol. Its hashes are
precomputed by `tools/mkshare.sh` into `SHARE.TXT`, because Python has no
Tiger and the whole point of the demo hub is that it needs nothing but
python3. It refuses `CGET tthl` for the same reason -- which is how it
found two queue bugs: a refusal left the file undownloadable, and leaves
that yielded no plan marked it DONE without fetching anything.

`make test-v86-sound` is the Sound Blaster. v86 emulates an SB16 at the
standard address, and the guest's `BLASTER` line is set for it, but v86
does **not** implement the 8237's count register -- it reads back as a
constant. The mixer notices (the count not moving for 250ms) and times the
ring from the clock instead, saying so in door 7 and in its reports:
`(timed: no DMA count)`. The gate measures what the mixer actually
delivers: 22,047 frames a second against the 22,050 the browser image asks
for.

### Game MIDI

v86 emulates an MPU-401 that answers a game's probe at 0x330 and discards
every data byte:

```js
port3x0_write = function(a){ dbg_log(a) }                    // discarded
port3x1_write = function(a){ 255===a && (buf.clear(), buf.push(254)) }
```

That is worse than having no interface at all. A game offered "Roland
MPU-401", finds one, and plays perfect silence; with nothing there it would
have fallen back to the Sound Blaster.

So the page takes the bytes itself. v86's I/O table is a plain object per
port whose handler the CPU calls, so `web/midi.mjs` wraps
`io.ports[0x330].write8` from outside the engine -- no patched vendor file,
no fork, and the original handler still runs, which is what keeps the
game's probe working. `web/synth.mjs` plays the result through a SoundFont
in an AudioWorklet (`web/midiworklet.mjs`), or `web/webmidi.mjs` sends it
out of the browser to a synthesiser the visitor owns.

The second needs no 40MB download and sounds better than anything this
project can ship, because it is not this project doing the synthesis: a
1994 DOS game drives a real SC-55 with an emulator and a browser in
between. Safari has no Web MIDI. Firefox and Chrome may ask, and may grant
notes while refusing sysex -- which matters, because an MT-32 game uploads
its patches as sysex, so the page counts what it had to drop and says so
rather than letting the music play with the wrong instruments.

Three gates, because each part fails differently:

```sh
make test-v86-midi    # the stream, and then the sound
make test-v86-doom    # a real game's soundtrack
make test-pages       # among others: the stream reassembly and the
                      # Web MIDI sink, with a stub for the browser
```

`make test-v86-midi` boots `MIDITEST.EXE` -- the same program the DOSBox-X
MIDI gate uses -- and requires every byte back in order: `c0 13`, `b0 07
7f`, three note-ons, three note-offs, twice, then sixteen all-notes-off.
Then it renders those messages, with the timing they arrived with, through
the page's own synthesiser and hands the audio to
`test/dos/midirms.py --expect-sound`: the same listener that judges the
DOSBox-X path.

`make test-v86-doom` is the claim that matters. BOOM 2.02 (the GPL Doom
engine; the FreeDOS package ships a free WAD with it) plays its title music
with no input, and the rig measures what comes out:

```
  7271 bytes, 2430 messages, 1166 notes
  music starts at 15.8s, 60.5s audible, 100% of the run after that,
  609-1830 RMS
  continuous, varying music: a game's soundtrack
```

**One number makes the difference.** `BOOM.CFG` ships `music_card = -1`,
autodetect -- and autodetect inside v86 finds the SB16 and picks an FM
device v86 does not implement, so Doom plays happily in silence. `6` is
`MIDI_MPU` in Allegro 3's driver numbering. `tools/mkv86img.sh` therefore
puts a `BOOMMIDI.CFG` on the image (the package's own config, that number
changed) and `PLAY BOOM` installs it after unpacking. Doom needs no extra
memory for this: measured, it plays its music in the same 16MB the client
gets.

`make test-relay` exercises the relay alone: it speaks the client half of
Wisp v1 over a hand-rolled WebSocket, runs an ADC handshake through the tunnel
against the stub hub, and checks the things worth checking: initial `CONTINUE` on stream 0, `CONTINUE` after `CONNECT`, `CLOSE
0x48` for unmapped destinations, UDP refusal, path-traversal containment, the
COEP header, and that the relay survives stream and socket teardown.

A browser is a poor test harness, so neither test needs one. The relay was
built and verified this way before any of the v86 side existed.

## Known limits

- **UDP is not forwarded.** v86's Wisp client does not implement it yet, so
  ADC search results over UDP (`URES`) cannot arrive in the browser build.
  Search over TCP (`DRES` via the hub) is unaffected. The relay answers UDP
  `CONNECT` with `CLOSE 0x48` rather than hanging.
- **No OPL.** v86 has no FM synthesis, so a game that picks AdLib or
  "Sound Blaster music" is silent here however well it works on hardware --
  which is exactly what Boom's autodetect does if you let it. MIDI is the
  way out of that (see above), because the notes can be taken off the port
  and played by something that does exist.
- **Our own music** is PCM from our tracker mixer, 8-bit mono at 22,050 Hz
  -- twice the rate a real 486 gets, because the machine under a browser tab
  can afford it.
- **No readable DMA count.** See `make test-v86-sound` above: the mixer
  falls back to the clock, which is accurate enough to feed a ring and not
  accurate enough to be called a position. On real hardware the counter is
  read.
- **Passive mode only.** Nothing can open a connection *into* the guest, so
  active mode and `CTM` cannot work here — the same constraint as DOSBox-X
  with slirp.
- **Verified headlessly, not yet in an actual browser.** `make test-v86` and
  the gates above boot these exact images in v86 under Node -- Node has a
  global `WebSocket`, which is all the Wisp adapter needs -- and
  `make test-pages` does it again with the published bundle, served over
  HTTP and read in blocks. The page uses the same configuration, but nobody
  has clicked Boot in Chrome: the layout, the buttons and the audio output
  are the untested part.

## Pinned versions

`tools/fetchv86.sh` pins the engine (`V86_VERSION`, default 0.5.470 from npm)
and records what it fetched in `web/vendor/VERSIONS.txt`. v86's config shape
has changed before; a silently-updated emulator is a bad surprise. BIOS images
come from the v86 repository, which does not ship them on npm.
